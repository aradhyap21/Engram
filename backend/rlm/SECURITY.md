# Security & Sandboxing for RLM

The Recursive Language Model (RLM) API feature executes Python code generated by an LLM in response to potentially arbitrary user input (data and queries). 

## Defense in Depth

The current sandbox implementation in `engine.py` operates under a **defense-in-depth** philosophy rather than providing a hardened, adversarial boundary. The code execution is isolated using the following mechanisms:

1. **Subprocess Isolation**: Code is executed in a separate `subprocess` rather than in the main API process.
2. **Restricted Built-ins**: The execution environment drops dangerous modules such as `os`, `sys`, and `socket`, and overrides built-ins like `open` and `__import__` to restrict filesystem and network access.
3. **Timeouts**: Execution steps are strictly bounded by a wall-clock timeout (`max_wall_clock_seconds`).

## Limitations

Because this system runs on Windows without relying on advanced containerization (e.g., Docker, Windows Containers) or OS-level Job Objects:
- **Memory Limits** are not strictly enforced by the OS. The output is bounded by API limits, but the subprocess could technically attempt to consume large amounts of memory.
- **Escape Vectors**: Python's dynamic nature means that restricting `__builtins__` is famously circumventable (e.g., via `__subclasses__` on base objects) by a determined, adversarial actor.

## Production Requirements

Before this feature is exposed to arbitrary third-party/company input in a production environment, **it requires a dedicated security review**. 

To be production-ready, this feature should be deployed where the subprocess runs inside an ephemeral, tightly constrained microVM (e.g., Firecracker) or a heavily restricted container (e.g., gVisor) with:
- No external network access.
- Read-only filesystem mounts.
- Strict kernel-level cgroups for CPU and memory usage limits.
